# 销售运营 Agent MVP

代码基础来自 [zhougeek-bot/open-sales-assistant](https://github.com/zhougeek-bot/open-sales-assistant)，保留其 MIT 许可证和现有前台咨询/知识库能力。

## 目标

把现有的销售助手 starter 改造成一个可用于客户访谈和小范围试用的销售运营工作台。当前先验证一件事：小型 B2B 团队是否愿意为“减少线索漏跟进，并更快准备下一步沟通”持续使用和付费。

初始用户假设是北京及周边、依赖表格和微信沟通、销售人数较少的 B2B 服务或软件团队。这只是待验证的假设，不代表已经选定行业。

## 当前 MVP

- 手动创建和编辑线索：联系人、公司、电话、邮箱、来源、阶段、负责人、意向等级、需求摘要、下次跟进日期。
- 从 CSV 或 XLSX 导入线索，按手机号或邮箱跳过重复记录，并返回无效行数量。
- 查看所有未关闭线索，以及今天到期和已逾期的跟进队列。
- 记录电话、微信/消息、会议、邮件和其他沟通，并保留记录人和时间。
- 根据线索、历史沟通和已审核销售知识生成下一步建议、待确认信息和消息草稿。
- AI 草稿必须由销售人员核对；本版本不连接外部渠道，也不会自动发送。
- 使用 AI 建议时，需求摘要、销售阶段、意向等级和沟通记录会发给部署者配置的模型服务；联系人姓名、公司、电话、邮箱字段不会单独作为模型上下文发送。
- 原有客户咨询和知识库能力保留，但与新建的销售线索数据分开。

## 数据与模块边界

新增数据集合：

- `leads`：线索资料、阶段、负责人和下次跟进时间。
- `leadActivities`：关联线索的沟通记录。

新增后台接口统一放在 `/api/admin/leads` 下。线索和沟通记录位于统一 storage 接口之后，支持默认 JSON 文件和可选 PostgreSQL。`schemaVersion` 为 4；旧数据会迁移并为用户、负责人和团队字段补齐默认值。当前 PostgreSQL 把完整状态放在一条 JSONB 记录中。

当前不把线索复用为 `students`。原有公开咨询入口仍依赖学员登录、聊天和课程流程，混用两个实体会让 CRM 操作影响客户登录和历史咨询。

## 暂不做

- 自动抓取或群发微信消息。
- 全功能 CRM、复杂销售漏斗和收入预测。
- 针对某一垂直行业的字段、话术和训练数据。
- 多租户 SaaS、多团队隔离和高并发生产环境。

## 生产化前置工作

存储适用范围：JSON 模式用于本地演示和单进程试用；PostgreSQL 模式支持单团队小范围多人试点，数据库行锁会串行化所有写请求，写入量高或 AI 请求较慢时可能排队。大规模使用前需要把线索、成员和活动拆为关系表，并完成真实 PostgreSQL 集成验证。API Key 继续只放在环境变量，不写入业务数据。

## 验证指标

访谈招募渠道、话术、执行节奏和首轮判定规则见[客户验证执行包](客户验证执行包.md)。

试用阶段优先记录：

- 线索导入后，销售是否设置了负责人和下一次跟进。
- 到期跟进是否被按时处理。
- AI 草稿是否经人工修改后被实际采用。
- 销售每次准备下一步沟通花费的时间是否下降。
- 团队是否愿意每周持续使用，并为解决该问题付费。

只有在访谈和试用中发现相同流程反复出现，才为该类团队增加行业模板或 CRM/消息渠道连接器。
