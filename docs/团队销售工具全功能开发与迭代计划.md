# 团队销售工具全功能开发与迭代计划

更新时间：2026-10-23

## 1. 项目定位

Open Sales Assistant 的目标是提供可自部署的智能销售助手。新增的通用线索工作台仍处于验证阶段，目标团队和行业尚未定型；当前不建设商业 SaaS 平台。

它要解决的问题：

- 销售资料分散，销售新人很难快速掌握产品和话术。
- 客户咨询重复，团队需要统一、可维护的 FAQ 和顾虑应对。
- AI 可以帮助整理资料、生成待审核建议，但不能自动覆盖正式知识库。
- 小团队希望用一个简单系统管理销售资料、客户咨询、跟进记录和基础数据。

当前默认数据是培训机构销售场景，用作开源 demo。后续可逐步替换为更多行业示例，例如课程、软件、门店服务、顾问服务和 B2B 解决方案。

## 2. 当前能力

- Node.js + Express 单体服务。
- 前台咨询页、登录页和后台管理页。
- 默认 JSON 文件存储，可选 PostgreSQL adapter；后者将全量状态存于单条 JSONB 记录。
- 素材上传、AI 分析、知识库建议审核。
- 销售话术、FAQ、顾虑应对、知识摘要维护。
- 客户资料、聊天记录、AI 画像、跟进记录。
- 通用销售线索、负责人、阶段、意向等级和下次跟进日期。
- 超级管理员、主管和销售角色；销售只能访问自己负责的线索。
- CSV/XLSX 导入、待跟进队列、沟通时间线和人工审核的 AI 跟进草稿。
- 基础后台操作日志，记录关键写操作。
- 证书查询作为 demo 业务模块。
- 数据导出、手动备份和基础部署文档。
- JSON 继续作为默认轻量模式；PostgreSQL、JSON 数据迁移、团队成员权限和备份恢复已实现。

## 3. 迭代路线

### P0：开源可运行版本（已完成）

目标：让新用户克隆仓库后能在本地跑起来，理解 demo 数据和完整销售知识库流程。

要做：

- README、贡献指南、安全说明、许可证补齐。
- Demo 数据标注清楚，避免被误认为真实业务数据。
- `.env.example` 使用本地默认地址。
- 保留 JSON 数据库，便于快速试用。
- 增加基础测试和健康检查说明。

### P1：用户验证与规模化准备

目标：验证哪类小团队会持续使用线索工作台，再决定协作和垂直化范围。

要做：

- 按[客户验证执行包](客户验证执行包.md)访谈小型 B2B 团队，核对线索从哪里来、谁负责跟、现在如何安排下一步。
- 用试用数据衡量到期跟进完成率、AI 草稿采纳率和准备时间变化。
- 以单团队低到中等写入量为边界开展小规模试点，验证成员权限和备份恢复。
- 随数据量和并发增长把 PostgreSQL JSONB 状态拆为关系表，并补真实数据库集成测试。
- 根据访谈中反复出现的任务，决定是否增加行业模板或渠道连接器。

### P2：知识库和 AI 质量增强

目标：让团队可控地使用 AI，而不是让 AI 直接改正式内容。

要做：

- 知识库版本历史和回滚。
- AI 建议采纳前可编辑。
- 素材编辑、搜索、批量操作。
- 知识冲突检测增强。
- Prompt 和回答质量评测样例。
- AI 用量日志和成本估算。

### P3：数据和部署增强

目标：让团队自部署更稳，降低数据丢失风险。

要做：

- 数据迁移机制持续完善。
- 备份恢复后台。
- 改进操作日志筛选、详情和导出。
- 完善 PostgreSQL 关系表迁移，但不移除 JSON 存储。
- 改进 Docker 部署和容器化自部署示例。
- 生产部署 checklist。

### P4：生态连接器

目标：让销售助手可以接入团队已有工具。

要做：

- 表单线索导入。
- Excel/CSV 客户和资料导入。
- CRM 示例连接器。
- 企业微信、飞书或 Slack 通知示例。
- MCP connector 示例，用于把销售资料和客户上下文暴露给 AI 工具。

## 4. 开源维护目标

- 每个迭代都保持自部署可用。
- 保留 JSON 存储，方便本地 demo、轻量自部署和贡献者测试。
- 不把客户数据、商业部署配置或私有 API key 放入仓库。
- 新功能优先用 demo 数据和可复现测试验证。
- 通过 issue 和 PR 维护路线，积累真实开源协作证据。
- 用 Codex 辅助 issue triage、PR review、测试生成、文档更新和 release notes。
